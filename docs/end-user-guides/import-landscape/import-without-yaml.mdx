# Import Cloud Foundry Org

In this guide, we assume an
> already existing Cloud Foundry Organization with
>- one or more _spaces_
>- a deployed _app_
>- a _service instance_
>- _org and space role_ assignments.

We **want to orchestrate them using the Crossplane Cloud Foundry Provider** and control plane methodology.

We will achieve this by following these 3 steps

#### 1. Generate Yaml with Export CLI
We will use the CLI Exporter: `xpcf` to **scan & generate the yaml definition** of Cloud Foundry resources that already exist in our running Organization.

#### 2. Observe and Review
We will review the resources and apply them to the Cloud Foundry Crossplane Provider in observe mode.
The provider will compare with the actual API in **read-only way and verify correctness of yaml.**

#### 3. Orchestrate from code
We can now make our yaml files the source of truth to **actively orchestrate** our cloud landscapes using the Crossplane Cloud Foundry provider.


## Before you start

- Install the [Cloud Foundry CLI](https://docs.cloudfoundry.org/cf-cli/install-go-cli.html)
- ControlPlane running the Cloud Foundry Crossplane Provider and [authenticate](../configure-provider-cf.mdx) your Organization

:::warning ensure Access

Make sure the Cloud Foundry provider's ProviderConfig uses a technical user that has admin access in the Organization of interest.

:::



## 0. Install the exporter

Run the `xpcf` exporter directly with Nix:

```bash
nix run github:SAP/crossplane-provider-cloudfoundry#xpcf -- --help
nix run github:SAP/crossplane-provider-cloudfoundry#xpcf -- export --help
```

:::tip

Pin a released version by appending a tag, e.g. `#xpcf` → `/v0.3.4#xpcf`.

:::

## 1. Generate resources

![import](/img/import-cli-cf-yaml.png)

#### Login to Cloud Foundry

Persist your Cloud Foundry credentials once with the `login` subcommand. You will be prompted for the API endpoint, username, and password:

```bash
xpcf login
```

#### Target org

`xpcf` targets your existing Organization by name. The pattern is a regular expression.

<Tabs groupId="cf-export-org">
<TabItem value="pattern" label="By name" default>

Add `--org '.*dev.*'` to the export command to select Organizations whose names contain `dev`.

```bash
xpcf export \
  --kind organization \
  --org '.*dev.*'
```

</TabItem>
<TabItem value="all" label="All orgs">

Use `--org '.*'` to match every Organization you can access.

```bash
xpcf export \
  --kind organization \
  --org '.*'
```

</TabItem>
</Tabs>

#### Choose resources

Export all supported kinds or only individual ones.

<Tabs groupId="cf-export-resources">
<TabItem value="all" label="All resources" default>

Repeat `--kind` for each supported resource kind to capture the whole Organization:

```bash {4-9}
xpcf export \
  --org '.*dev.*' \
  --space '.*' \
  --kind organization \
  --kind space \
  --kind app \
  --kind serviceinstance \
  --kind orgrole \
  --kind spacerole
```

</TabItem>
<TabItem value="pick" label="Pick resources">

Choose a subset of kinds. This example exports `Organizations`, `Spaces`, and `Apps`:

```bash {4-6}
xpcf export \
  --org '.*dev.*' \
  --space '.*' \
  --kind organization \
  --kind space \
  --kind app
```

</TabItem>
</Tabs>

:::tip Resources link by reference

The exporter links resources through Crossplane references, such as `orgRef` and `spaceRef`, instead of technical GUIDs. This keeps the generated landscape internally linked and meaningful.

:::

## 2. Apply in observe mode

![observe](/img/import-cli-cf-observe.png)

Apply the reviewed manifests directly to your control plane:

```bash
kubectl apply -f landscape.yaml
```

With `Observe`, Crossplane reads the existing resources without creating, updating, or deleting them.

### Verify observation

Check the resources you applied:

```bash
kubectl get managed
```

Apply the same gates to the deployed resources before enabling management:

## 3. Enable management

![orchestrate](/img/import-cli-cf-observe-1.png)

Change `managementPolicies` from `[Observe]` to `["*"]` for each resource you want Crossplane to manage, keeping the IDs, names, references, and configuration verified during observation. The Organization example below highlights this change.

```yaml {8-9}
apiVersion: cloudfoundry.crossplane.io/v1alpha1
kind: Organization
metadata:
  name: demo-org
  annotations:
    crossplane.io/external-name: "<organization-guid>"
spec:
  managementPolicies:
    - "*"
  providerConfigRef:
    name: default
  forProvider:
    name: "<existing-org-name>"
```

**`"*"` permits all supported actions, including creation, updates, and deletion.**

Re-apply the updated manifests:

```bash
kubectl apply -f landscape.yaml
```

After the control plane reconciles, verify the resource conditions and Cloud Foundry state again before relying on active management.

## Troubleshooting

Rerun the export with `--verbose` for diagnostic output.

| Symptom | Check |
|---|---|
| Authentication or permission failure | Re-run `xpcf login`, verify the API endpoint, and check Organization permissions. The provider's credentials must also have access. |
| No resources returned | Check org/space access and selection patterns; widen the `--org` and `--space` regular expressions. |
| References not resolved | Export the referenced kind in the same run (e.g. export the Organization alongside its Spaces) so `orgRef`/`spaceRef` can be linked. |
